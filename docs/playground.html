What to check

This one checks the version actually installed, not just the declared range — so an npm overrides entry (or Yarn resolutions, or pnpm's own overrides) can't sneak a banned version past a declared range that looks safe, and can't get an innocent package falsely flagged either. See the two old-utils cards above. Before anything is installed on disk yet, this falls back to just the declared range, same as before.

Simulate the environment

Not a flag you set — the real tool auto-detects this from a .pnp.cjs/.pnp.mjs file at the repo root. Yarn PnP has no node_modules, so the tool can't check what's actually installed at all. It degrades instead of guessing wrong: the peer-dependency check turns itself off (with a warning), and the "banned by version range" check falls back to just the declared range instead of the installed version — same as if overrides/resolutions support didn't exist. Flip this on to see both effects on the two old-utils cards above.

Where to look for version mismatches

Only affects the "different versions of the same package" check. Uncheck a box to stop comparing that part of package.json.

Ignore a package by name

Example: your team knows left-pad has different versions on purpose, and wants the tool to stop complaining about it. If you type a name that isn't actually mismatched right now (try request), it just does nothing — it won't error out, so you don't have to remember to clean it up later.

Skip an entire package

Example: scratch-tool is a throwaway internal script — tell the tool to pretend it doesn't exist for every check.

Auto-fix

Only fixes version mismatches, by rewriting package.json files to the newest version already used somewhere. Blocked packages and peer-dependency problems always need a human.
